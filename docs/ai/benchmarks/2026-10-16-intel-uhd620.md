# Eqho on an Intel-only laptop — results (2026-10-16)

Dell Latitude 5400 · i7-8665U · Intel UHD Graphics 620 · tested build = `Eqho-private@efae469` (reports 0.8.8)
Run by a Claude Code session on the laptop, following [`TEST-PLAN.md`](2026-10-16-intel-uhd620/TEST-PLAN.md). Times are CEST.

## TL;DR

1. **Accuracy is the same as on the main PC** for both engines (within ±0.3 pp WER on the same 60+60 clips).
2. **whisper.cpp really runs on the Intel GPU** (Vulkan device = UHD 620, GPU 3D engine at 94–99 % during the runs,
   CPU at 6–15 %) — but it is **slow: 0.30× realtime**, about 26 s per call no matter how short the clip.
3. **faster-whisper on the CPU is ~1.6× faster** than whisper.cpp on the iGPU here (0.48× realtime, ~14–19 s per
   call) with the same accuracy. **Auto currently picks whisper.cpp on this PC — the slower engine.**
4. **Step 6 (real dictation) failed 3/3, and it is an app bug, not the test:** Eqho transcribed every clip but
   **dropped the text** because `stop()` only waits `STOP_JOIN_TIMEOUT = 5.0` s for the final flush
   (`src/transcriber.py:35`, `:546–550`). On this laptop a transcription takes 26 s, so **every dictation types
   nothing**, silently — with either engine.
5. Settings files with a UTF-8 BOM are rejected as "corrupted" and replaced by defaults (`src/settings.py:416`).
   The TEST-PLAN's own `Set-Content -Encoding utf8` (Windows PowerShell 5.1) produces exactly such a file.

**Recommendation:** on PCs like this one, Auto should pick **faster-whisper (CPU)**. More important than the engine
choice: fix the 5 s stop-flush drop, and use a smaller default model on this hardware class — with
distil-large-v3 even the faster engine needs ~14–19 s per utterance here.

## 5. Accuracy and speed (step 4)

Same 60 clips per set as the main PC: the `utt_id` order matched the first 60 rows of each reference CSV exactly.
0 failed and 0 empty clips in all 4 runs. Model: `distil-large-v3` in settings. whisper.cpp maps that to
**`large-v3-turbo`** (`_WHISPERCPP_NAME`), so the two engines run different models, on both PCs.

| Engine | Set | WER here | WER main PC | Speed here | Speed main PC | Model load here |
|---|---|---|---|---|---|---|
| whisper.cpp (Vulkan → Intel UHD 620) | clean | **2.40 %** (34/1414) | 2.55 % (36/1414) | **0.34×** realtime (RTF 2.968) | 20.2× (RTF 0.0495) | 70.4 s (incl. 1.6 GB download) |
| whisper.cpp (Vulkan → Intel UHD 620) | other | **3.41 %** (37/1085) | 3.32 % (36/1085) | **0.27×** (RTF 3.759) | 26.1× (RTF 0.0382) | 4.9 s (cached) |
| faster-whisper (CPU int8, 4 threads) | clean | **2.48 %** (35/1414) | 2.48 % (35/1414)¹ | **0.48×** (RTF 2.077) | 18.4× (RTF 0.0545)¹ | 62.1 s (incl. 1.5 GB download) |
| faster-whisper (CPU int8, 4 threads) | other | **4.52 %** (49/1085) | 4.79 % (52/1085)¹ | **0.48×** (RTF 2.091) | 13.0× (RTF 0.0768)¹ | 21.1 s (cached)² |

¹ The main-PC faster-whisper reference ran on NVIDIA CUDA (`gpu-*.csv`). Here it ran on the CPU.
² The cached faster-whisper load includes a warm-up inference on 1 s of silence. On this CPU, one inference costs
about 14 s (see below), so most of the 21 s is warm-up.

**Both sets combined (959.9 s of audio):**

|---|---|---|---|---|

→ **faster-whisper is 1.59× faster overall** here (1.43× on clean, 1.80× on other). The WER difference matches the
main PC (turbo is slightly better on test-other on both machines), so it comes from the model, not this hardware.
Per clip, the error counts differ from the reference on only 0–2 clips per run.

### Time per call, not per second of audio

Each call has a large fixed cost: Whisper always encodes a full 30 s window. A least-squares fit of transcribe time
against clip length:

| Run | min / median / max per clip | fit | clips < 4 s |
|---|---|---|---|
| whisper.cpp clean | 25.4 / 26.6 / 30.2 s | 26.0 s + 0.11 × audio_s | 26.0 s avg |
| whisper.cpp other | 25.3 / 26.1 / 27.1 s | 25.6 s + 0.06 × audio_s | 25.7 s avg |
| faster-whisper clean | 12.6 / 19.1 / 24.9 s | ≈ 19 s flat (noisier run) | 19.9 s avg |
| faster-whisper other | 13.7 / 14.4 / 15.4 s | 14.1 s + 0.05 × audio_s | 14.3 s avg |

So on this laptop with distil-large-v3, **a 2-second "yes" takes ~26 s (whisper.cpp) or ~14–19 s (faster-whisper)**.
That is the real user-facing latency. "× realtime" averaged over 9 s clips hides it.

### Did whisper.cpp use the Intel GPU? Yes.

GPU and CPU load were sampled every ~2–3 s with `Get-Counter` (1848 samples, 13 invalid, skipped):

| Run | Duration | GPU 3D engine avg / max | GPU busy (> 20 %) | Shared GPU memory max | CPU avg |
|---|---|---|---|---|---|
| whisper.cpp clean | 28.2 min | 94 % / 110 % | 95 % of samples | 2256 MB | 15 % |
| whisper.cpp other | 26.2 min | 99 % / 110 % | 100 % | 2166 MB | 6 % |
| faster-whisper clean | 19.9 min | 2 % / 28 % | 0 % | 448 MB | 65 % |
| faster-whisper other | 14.9 min | 1 % / 3 % | 0 % | 314 MB | 55 % |

Every whisper.cpp log line shows `using Vulkan0 backend`. On Intel, the Vulkan work appears under the **3D** engine;
the "Compute" engine stayed at 0. The iGPU is saturated, so whisper.cpp is GPU-bound. faster-whisper uses 4 threads
(`_cpu_threads()` = 8 logical // 2), which is why the CPU sits at ~55–65 %, not 100 %.

The 4 runs took **89 minutes in total** (plan estimate: 30–60).

## 6. Real dictation on the desktop (step 6) — FAILED 3/3: text is dropped

Run with the owner's OK, `cfg-whisper.cpp`, `--clips 3 --gate-wer 0.25`. The script uses **Ctrl+Shift+F9**, not
Alt+Q (see its comment about the `keyboard` library dropping injected Alt events). Exit 1 after 185 s. System volume
was restored OK. Model ready in 6.0 s.

```
[clip 1] 1089-134686-0000: 10.4s audio   start latency 0.21s   FAILED: no text was injected
[clip 2] 1188-133604-0000: 10.7s audio   start latency 0.05s   FAILED: no text was injected
[clip 3] 121-121726-0000:   8.5s audio   start latency 0.03s   FAILED: no text was injected
```

What Eqho's own log ([`e2e/eqho.log`](2026-10-16-intel-uhd620/e2e/eqho.log)) shows for clip 1 (clips 2 and 3 are identical in pattern):

```
12:50:06 Dictation activated / Transcription started (session 1) / TEST AUDIO feeding 10.4 s
12:50:07 Speech detected                                  ← a partial (VAD phrase) transcription starts
12:50:19 Dictation deactivated                            ← test presses stop (clip + 2.5 s)
12:50:24 Transcription stopped.                           ← stop() gave up after STOP_JOIN_TIMEOUT = 5 s, session → 2
12:50:34 Partial transcript: 32 chars
12:50:34 Dropped result from closed session 1 (current: 2)
12:50:34 Flushing remaining 17.9s of audio on stop
12:51:01 Complete transcript: 163 chars (17.9s audio, transcribed in 27.05s)
12:51:01 Dropped result from closed session 1 (current: 2)   ← the full, correct-length text is thrown away
```

**Cause:** `Transcriber.stop()` joins the worker for at most `STOP_JOIN_TIMEOUT = 5.0` s
(`src/transcriber.py:35, 546`) and then bumps `_session_id` (`:550`). `_deliver()` (`:473`) drops every result from
the closed session. That guard exists so a late result can't land in the next dictation (F2). But on a machine where
one inference takes ≥ 5 s, it drops **every** final transcript. On this laptop that is any engine with
distil-large-v3 (26 s whisper.cpp, 14–19 s faster-whisper). The user sees nothing typed and gets no error.
Also, the in-flight partial was dropped and then the same audio was re-transcribed in the flush, so the user would
wait ~2 × 26 s even if delivery worked.

Also: `e2e-results.csv` contains only the header. Failed clips are not written as rows.

## 7. Errors and odd things, in order

1. **Settings with a UTF-8 BOM are treated as corrupt.** Windows PowerShell 5.1 `Set-Content -Encoding utf8` writes a
   BOM. `Settings.load()` reads with `encoding="utf-8"` (`src/settings.py:416`):
   `WARNING: Could not read settings … Unexpected UTF-8 BOM (decode using utf-8-sig)` → file moved to
   `settings.json.bad`, defaults used. With the TEST-PLAN's step-4 snippet as written, all four benchmark runs would
   have silently used default settings. I wrote the config files without a BOM instead
   (`[IO.File]::WriteAllText(…, UTF8Encoding($false))`) and checked each one loaded correctly before the runs.
   Users who edit `settings.json` in an editor that saves "UTF-8 with BOM" lose all their settings the same way.
   Fix: `read_text(encoding="utf-8-sig")`.
2. **whisper.cpp ignores `model_dir`.** `_WhisperCppBackend` calls `Model(name)` (`src/model_host.py:225`), so GGML
   models go to `%LOCALAPPDATA%\pywhispercpp\pywhispercpp\models\` (here: `ggml-large-v3-turbo.bin` 1.6 GB +
   `ggml-tiny.bin`), not to the configured model folder. From reading the code (not tested separately):
   `is_model_cached()` only checks the faster-whisper/CTranslate2 cache, so for the whisper.cpp backend the "cached"
   answer is about the wrong file.
3. **whisper.cpp ignores `beam_size` and `initial_prompt`.** `_WhisperCppBackend.transcribe` only passes `language`.
   The bench's `--beam-size 5` therefore applies only to faster-whisper.
4. **Speed on this hardware class** (see §5): ~26 s / ~14–19 s per call for distil-large-v3 / large-v3-turbo.
5. **Test-build smoke:** works; output is captured despite no console. `Eqho.exe` is unsigned and has no version
   resource. In Windows PowerShell 5.1, `Start-Process … -RedirectStandardOutput -PassThru` returns an **empty
   `ExitCode`** unless `$p.Handle` is touched before exit. The plan's snippet printed nothing for the exit code on
   the first try; with the handle cached it reads 0.
6. **`py` launcher not on PATH** in the same session right after the winget install. I used
   `%LOCALAPPDATA%\Programs\Python\Python313\python.exe` to create the venv.
7. **Hugging Face warnings** during the faster-whisper download: unauthenticated requests (HF_TOKEN), and the cache
   can't use symlinks on this account, so files are stored as copies.
8. **The 5-minute AC sleep timeout** would have suspended the run. I held a temporary keep-awake request
   (SetThreadExecutionState) from 11:38 to 12:45. The owner also raised the sleep timeout to 4 h. The timeline shows
   no gaps.
9. Get-Counter returned "data … not valid" for 13 of 1848 samples. These were skipped and didn't affect the
   averages.

## 8. Recommendation

**On a PC like this one (Intel UHD 620-class iGPU, `uma: 1`, `int dot: 0`, `matrix cores: none`, 4-core U-series CPU
with AVX2), Auto should pick faster-whisper (CPU), not whisper.cpp.**

- It is 1.6× faster (0.48× vs 0.30× realtime; ~14–19 s vs ~26 s per utterance) with the same accuracy.
- It doesn't occupy ~2.2 GB of shared GPU memory or saturate the iGPU that drives the desktop.
- Today `resolve_backend("auto")` returns whisper.cpp as soon as pywhispercpp is installed and the CPU has AVX2. A
  Vulkan device alone is not a good enough signal. Options: prefer faster-whisper when the only Vulkan device is
  `uma: 1` with no int-dot/matrix cores, or run a one-time calibration on first launch (one 30 s-window encode per
  engine, ~40 s here) and cache the winner. This is data from a single machine. AMD RDNA2/3 iGPUs may well favour
  whisper.cpp, so a calibration is safer than a vendor rule.

More important than the engine choice, for this hardware class:

1. **Fix the stop-flush drop (§6).** Scale the stop wait to the measured inference time, or deliver the late final
   result to its own session's target window as long as no new session has started. Show "transcribing…" while
   waiting. As it stands, Eqho is unusable on this laptop.
2. **Use a smaller default model on slow hardware.** Even the faster engine needs 14–19 s per utterance with
   distil-large-v3. Benchmark `small.en` / `base.en` on this laptop next. whisper.cpp's `audio_ctx` (a shorter
   encoder window for short clips) is also worth a test, since the fixed 30 s window is where the 26 s goes.
3. Accept a settings BOM (`utf-8-sig`), and give whisper.cpp the configured `model_dir` plus a matching
   `is_model_cached` check.
